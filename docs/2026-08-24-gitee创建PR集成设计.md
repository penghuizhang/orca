# Gitee「像 GitHub 一样创建 PR」集成设计

日期：2026-08-24
类型：实现设计（调研结论落地，待评审）
前置文档：[gitee-cli 结合方案分析](2026-08-24-gitee-cli结合方案分析.md)

## 0. 关键发现（决定方案形态）

探查 `src/main/source-control/` 与 `src/main/gitee/` 后，一个重要事实：

**Gitee 已经 90% 接进了 Orca 的「托管评审（hosted-review）」流程——也就是 GitHub 右栏「创建 Pull Request」那一整套。** 证据：

- `src/shared/hosted-review.ts`：`HostedReviewProvider` 联合类型**已含 `'gitee'`**，`HostedReviewForBranchArgs` 已有 `linkedGiteePR` 字段。
- `src/main/gitee/forge-provider.ts`：`giteeForgeProvider` 已实现 `resolveRepository` / `getReviewForBranch` / `getReviewByNumber`（**读 + 展示已通**），并被注册进 `FORGE_PROVIDERS`。
- 唯一卡住「创建 PR」的两点：
  1. `giteeForgeProvider.supportsReviewCreation: false`（第 8 行）
  2. 缺 `createReview` 方法（Gitea 的是 `createGiteaPullRequest`）

**而 Gitea（自托管 Git，与 Gitee 同构）已经完整实现创建能力**，走 HTTP + 已存 token，模板现成：`src/main/gitea/pull-request-creation.ts` + `forge-provider.ts` 的 `giteaForgeProvider`（含 `createReview: createGiteaPullRequest`、`supportsReviewCreation: true`）。

结论：**「像 GitHub 一样建 Gitee PR」最小改动 = 把 Gitee 接进同一套托管评审创建流，照抄 Gitea 模板**，而不是另起炉灶或硬塞 gitee-cli。

## 1. 推荐方案：完成既有 HTTP 接线（镜像 Gitea）

### 1.1 为什么走 HTTP 而非 gitee-cli（回应前一份分析）

前一份分析建议写路径用 gitee-cli（路线 B）。但看到架构后修正：

- Gitea 这个同构兄弟**就是用 HTTP 创建 PR**（`createGiteaPullRequest` → `requestHostedReviewJson`），Gitee 的 `src/main/gitee/` 也已有 PAT 认证的 HTTP 客户端。**沿用 HTTP 与代码库惯例一致、改动最小。**
- 避免把 Go 原生二进制打进 orca-s（Linux glibc≥2.31、Windows `runProcess`、PATH 隔离等打包负担）。
- PAT 已在 safeStorage，无需再经 `GITEE_TOKEN` 环境变量喂子进程。
- **gitee-cli 仍保留为手动终端工具**（已装 `~/.local/bin/gitee`），并作为详情对话框写操作的备选 transport（见第 4 节），但不是「应用内建 PR 按钮」的 transport。

### 1.2 用户体验（即「像 GitHub 一样」）

在右栏 source-control 面板：当工作树分支已推到 gitee.com 远程且 Gitee PAT 已连 → 出现 **「Create Pull Request」** 按钮（与 GitHub 同位置同交互）→ 弹出 composer（标题 / 描述 / base 分支选择，可读取 `.gitee/PULL_REQUEST_TEMPLATE.md`）→ 创建后自动关联 `linkedGiteePR`，看板/首页卡片显示该 PR 状态。这一切由现有 `use-create-pr-intent-*` + `hosted-review-creation.ts` 驱动，Gitee 只需在 forge-provider 暴露 `createReview` 即可点亮。

### 1.3 具体改动清单

| # | 文件 | 改动 |
|---|---|---|
| 1 | `src/shared/hosted-review-creation-providers.ts` | `HostedReviewCreationProvider` 联合类型加 `'gitee'`；`supportsHostedReviewCreation()` 的返回判断加 `\|\| provider === 'gitee'` |
| 2 | `src/main/gitee/forge-provider.ts` | `supportsReviewCreation: false` → `true`；加 `createReview: createGiteePullRequest`（import 新模块） |
| 3 | `src/main/gitee/pull-request-creation.ts`（**新建，镜像 gitea**） | 导出 `createGiteePullRequest(input: CreateHostedReviewInput): Promise<CreateHostedReviewResult>`：用 `normalizeHostedReviewBaseRef/HeadRef` + 从 connectionId 解析 `GiteeAuthConfig` + POST `/repos/{owner}/{repo}/pulls`（title/head/base/body）+ `mapGiteeReview` 映射结果 + 错误分类；导出 `isGiteeReviewCreationAuthenticated()`（读 `hasStoredGiteeCredential()`，非 env） |
| 4 | `src/main/gitee/api.ts` | `requestGiteeJson` 当前仅 GET（拼 query、无 body）。扩展支持 `method` + JSON body，或新增 `mutateGiteeJson<T>(config, path, body, method)`；`authHeaders` 已就绪 |
| 5 | `src/main/source-control/hosted-review-creation.ts` | 两处加 gitee case（现有 gitea 在 ~289 / ~325）：`providerMetadata` 返回 `providerName: 'Gitee'`、`authInstruction` 指向 Settings 的 Gitee PAT 卡片；`isProviderAuthenticated` 调 `isGiteeReviewCreationAuthenticated()` |
| 6 | i18n | `providerName` 沿用内联英文 'Gitee'（同 gitea 写法），新增 copy 极少；若有新增 key 跑 `sync:localization-catalog` |
| 7 | 测试 | 镜像 `hosted-review-gitea.integration.test.ts` 加 `hosted-review-gitee.integration.test.ts`；`giteeForgeProvider` 单测补 `supportsReviewCreation: true` + `createReview` |

### 1.4 约束核对（实施时逐条自查）

- 【约束】不禁用 oxlint max-lines；新建 `pull-request-creation.ts` 控制行数，超则拆（错误分类/映射单独文件）。
- 【约束】跨平台：本方案纯 HTTP，无子进程，天然跨 macOS/Linux/Windows，不涉及 `runProcess`/`child_process`。
- 【约束】en.json 不被破坏；新增 i18n key 后跑 `pnpm run sync:localization-catalog`（fork 键 gitee×N 保留）。
- 【约束】复用既有 `mapGiteeReview`（`forge-review-mappers.ts` 已 import）、`getGiteeRepoSlug`、凭据读取，不重复造轮子。
- 【风险】`requestGiteeJson` 改造成本低但需确认上游 GET 调用不受影响（扩展而非改写，默认 method=GET 保持原行为）。
- 【风险】Gitee API v5 与 Gitea 字段略有差异（issue number 字母数字、PR number 整数），`mapGiteeReview` 已处理，创建返回体按 `RawGiteePull` 解析即可。

## 2. 实施顺序（Phase 1 = 本设计核心）

1. 扩展 `api.ts` 支持 POST（`mutateGiteeJson`）。
2. 新建 `pull-request-creation.ts`（含 `isGiteeReviewCreationAuthenticated`）。
3. 改 `shared/hosted-review-creation-providers.ts` 注册 gitee。
4. 改 `gitee/forge-provider.ts` 翻 flag + 接 `createReview`。
5. 改 `hosted-review-creation.ts` 两处 gitee case。
6. 测试 + 三 typecheck + oxlint + build。
7. 验收：dev 模式下 gitee.com 仓库分支 → 右栏出现 Create Pull Request → 创建成功 → 卡片显示关联 PR。

## 3. 打开项（待你拍板）

- **A. transport 选择**：Phase 1 走 HTTP（推荐，镜像 Gitea）。是否仍坚持用 gitee-cli 作为创建 transport？若坚持，则改为 spawn `gitee pr create` 喂 `GITEE_TOKEN`，并需处理 orca-s 二进制打包。
- **B. base 分支默认**：Gitee 仓库默认 base 多为 `master`（gitee-cli 也是 fallback master），composer 应允许用户选 base。

## 4. 后续 Phase 2（「创建 PR 等」里的「等」）

详情对话框 GiteeItemDialog 的写操作（评论 / 合并 / 评审 / 指派）目前未做。两种落地：
- **2a. 继续 HTTP**：在 `src/main/gitee/client.ts` 加 `mergeGiteePullRequest` / `commentGitee...` 等（与创建同范式，零二进制）。
- **2b. 用 gitee-cli**：新建 `src/main/gitee/cli-runner.ts` spawn `gitee pr merge/comment/review` + `GITEE_TOKEN`，适合想要 AI 草稿/模板/多 host 的场景，但引入打包负担。

建议 Phase 2 也走 2a（HTTP 一致），gitee-cli 保留为手动工具与兜底。

## 5. 结论

「像 GitHub 一样建 Gitee PR」不需要引入新机制——Gitee 早已在托管评审流里占了位，只差 `supportsReviewCreation` 翻 true + 一个 `createReview`（POST 到 Gitee API v5，复用已存 PAT）。镜像 Gitea 模板约 7 处改动即可点亮右栏「Create Pull Request」按钮。gitee-cli 已装好，作为手动终端工具与 Phase 2 备选 transport，而非应用内按钮的必需依赖。
