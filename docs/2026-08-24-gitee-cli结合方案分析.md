# Gitee CLI（oschina/gitee-cli）结合 Orca 方案分析

日期：2026-08-24
类型：调研 / 影响分析（L2 剩余项落地路线）

## 1. 背景与现状

- 用户主战场在 Gitee，已完成的 Orca Gitee 集成（第一个二开任务，PR #1 已合 custom）是**纯 HTTP API v5 + PAT** 手写实现，落在 `src/main/gitee/`、`src/shared/gitee-api.ts`、`src/main/ipc/gitee.ts`。
- 已实现（读路径为主）：连接/PAT 验证、账号级 PR/议题聚合列表、仓库列表、**详情对话框**（对话/文件/提交 4 个 IPC）、看板形态对齐 GitHub。
- **未实现的 L2 写操作**（来自 `orca-gitee-integration.md` 末尾清单）：PR/issue URL 解析进 linkedGiteePR、**创建 PR**、评论/标签管理、**合并与评审操作**、从 Gitee issue 创建 worktree、里程碑（项目页签）、「分配给我」筛选、OAuth2 登录。

本次发现：**Gitee 官方已发布 CLI `oschina/gitee-cli`**（MIT，Go 1.25+，平台 macOS/Linux/Windows），正好是 `gh` 之于 GitHub 的对应物。已安装到本机：

## 2. gitee-cli 能力对照

| 命令组 | 子命令 | 覆盖 Orca 现状 / L2 待办 |
|---|---|---|
| `auth` | login/logout/status/token | Orca 已有 PAT（safeStorage）；**可复用，不重复实现登录 UI** |
| `pr` | list/view/**create**/**edit**/**close**/**reopen**/**merge**/**review**/**comment**/diff/fetch/checkout | list/view 已有（HTTP）；**create/merge/comment/review/edit/close 即 L2 写操作** |
| `issue` | list/view/**create**/edit/close/reopen/**assign**/comment | list/view 已有；**create/assign/comment 即 L2** |
| `repo` | list/view/clone/**create**/**fork**/delete | 看板不动；create/fork 可作「从 issue 开 worktree」前置 |
| `release` / `ssh-key` / `search` / `api` | — | 暂不需要；`api` 可作兜底（raw V5 调用） |
| `ai` | prompt/--chat | 可对接 OpenAI 兼容模型生成 PR 描述（可选，二期） |

关键参数（已实测 `--help`）：
- `gitee pr create -t 标题 -b 正文 --base main --head 分支 --assignees 张三 --testers 李四 --draft --json`
- `gitee pr merge <number> -m merge|squash|rebase --delete-branch --json`
- 仓库定位：`gitee pr ... -R owner/repo`（全局 flag，README 示例确认）
- 非交互：`--json` 输出结构化结果；诊断信息走 stderr，stdout 保持可解析

## 3. 结合的核心机理（已验证可行）

1. **复用已存 PAT，零额外凭据管理**
   gitee-cli 读取环境变量 `GITEE_TOKEN`（源码 `internal/config/config.go:142` 直接 `os.Getenv("GITEE_TOKEN")`）。Orca 已把 Gitee PAT 存于 safeStorage，主进程读取后**以 `env.GITEE_TOKEN` 传给子进程**即可，无需写入 `~/.config/gitee/credentials.yml`，也不需再让用户登录一次。
   辅助环境变量：`GITEE_CONFIG_DIR`（隔离配置，避免污染用户全局）、`GITEE_API_PREFIX`（私有部署前缀）、命令级 `--hostname`（多 host）。

2. **对标 Orca 现有 `gh` 调用范式**
   Orca 的 GitHub 路径在 `src/main/github/gh-utils.ts` 用 `ghExecFileAsync`（`src/main/git/runner`，WSL 感知 + 并发队列 + AbortSignal + 错误分类 + JSON 解析）spawn `gh`。Gitee 写路径可建**对等的 `src/main/gitee/cli-runner.ts`**：用工程统一的 `runProcess`/`spawnProcess`（满足 AGENTS.md 跨平台 + Windows `windowsHide` 约束）spawn `gitee`，复用同一套并发/abort/错误解析骨架。

3. **读/写路径拆分**
   看板、详情等**读路径**继续用现有 HTTP 客户端（已验证、稳定、无外部二进制依赖）；**写路径**（创建/合并/评论/评审/指派）改走 `gitee` 子进程。这是最小风险、最快见效的切法。

## 4. 三条路线对比（推荐 B）

- **A. 全量切 gitee-cli（读也换）**：统一技术栈，但推翻已验证的 HTTP 读路径，回归风险大、收益低。❌ 不推荐。
- **B. 写路径走 gitee-cli，读路径保留 HTTP（推荐）**：L2 写操作直接获得 AI 草稿、PR 模板、多 host、重试/限流等免费能力；改动局限在新增 IPC + 一个 cli-runner；不触碰已稳定的看板/详情。✅ 推荐。
- **C. 纯 HTTP 扩展（不引入 CLI）**：继续在 `client.ts` 手写 POST 端点。可行但要把 gitee-cli 已解决的边界（合并三策略、评审、指派、模板）重写一遍，维护成本高。⚠️ 备选。

## 5. 落地清单（路线 B，待你评审后实施）

新增主进程能力（每个对应 1 个 IPC + preload 方法 + client 函数）：
1. `gitee pr create` → 详情/看板「创建 PR」按钮（标题/正文/base/head/assignees/draft）
2. `gitee pr merge` → 详情对话框合并操作（merge/squash/rebase + 删源分支）
3. `gitee pr comment` / `gitee issue comment` → 详情对话框发表评论（现有对话页签只展示，补写入）
4. `gitee pr review` / `gitee issue assign` → 评审/指派（详情对话框扩展）
5. `gitee pr edit` / `close` / `reopen` → 状态操作
6. `gitee issue create` / `assign` → 从 issue 创建 worktree 前置 + 指派
7. URL 解析：粘贴 `gitee.com/owner/repo/pulls/N` 进 `linkedGiteePR`（复用现有 `repository-ref.ts` 思路，CLI `pr view -R ... -j` 或 HTTP 均可）

复用不变：看板聚合（HTTP）、详情 4 个 IPC（HTTP）、Settings PAT 卡片（仍 safeStorage，仅新增「导出到 GITEE_TOKEN」一处读取点）、官方图标、项目选择器。

## 6. 打包与分发（orca-s 必须处理）

gitee-cli 是 **Go 原生二进制**，Orca 当前不依赖它。要 `orca-s.app` 内可用，三平台都需解决「二进制在场」：

- **macOS**：`build-orca-s.mjs` 增加一步，把 `~/.local/bin/gitee`（或 CI 下载的对应 arch dmg/zip 内二进制）拷入 `resources/` 并随 app 打包；主进程用 `process.resourcesPath` 定位，回退到 `PATH` 上的 `gitee`。
- **Linux**：注意 glibc floor = Ubuntu 20.04 / 2.31（AGENTS.md 硬性约束）。Go 静态二进制通常无此问题，但需确认官方发布物非动态链接；CI 在 20.04 runner 上验证。
- **Windows**：用 `runProcess`/`spawnProcess` 启动 `.exe`，同样走 `resources/` 内嵌 + PATH 回退；禁止 `child_process` 直连（AGENTS.md ratchet 测试）。
- **代理**：gitee-cli 走系统代理（与 Orca 一致）；若用户设了 `httpProxyUrl`，需确认 CLI 也读同一代理或显式传 `HTTP_PROXY`。

## 7. 风险与约束清单（实施前自查）

- 【约束】Windows 子进程必须走 `runProcess`/`spawnProcess`，禁 `child_process` 直连 —— cli-runner 复用 `src/main/git/runner` 或 `shared/child-process`。
- 【约束】跨平台：spawn 时不假设 `/` 或 `\`；macOS 用 `metaKey`、其余 `ctrlKey` 的快捷键逻辑不受影响（仅新增按钮）。
- 【约束】Linux native 二进制 glibc ≥ 2.31；Go 静态链接通常满足，CI 验证。
- 【约束】不禁用 oxlint max-lines；新增 cli-runner 单文件控制行数，超则拆分（如 `pr-commands.ts` / `issue-commands.ts`）。
- 【约束】en.json 不被破坏；新增 i18n key 后跑 `pnpm run sync:localization-catalog`（fork 键 gitee×N 保留）。
- 【风险】gitee-cli v0.2.3 仍早期，命令/flag 可能变动；实施时以当时 `--help` 实测为准，并在 cli-runner 内做最低版本探测（`gitee --version`）。
- 【风险】`GITEE_TOKEN` 通过 env 传入子进程，需确保不误入日志/崩溃上报（与现有 PAT 处理一致，避免明文落盘）。
- 【风险】orca-s 与官方 orca 数据隔离；gitee-cli 的 `GITEE_CONFIG_DIR` 应指向 orca-s 专属目录，避免与用户全局 gitee 配置串扰。

## 8. 结论

gitee-cli 是填补 L2 写操作缺口的最优杠杆：**Orca 用 `gh` 管 GitHub、用 `gitee` 管 Gitee，范式统一**；`GITEE_TOKEN` 环境变量让 Orca 已存的 PAT 零成本复用；读路径不动，风险收敛在新增写 IPC + 一个 cli-runner + 打包内嵌二进制。建议走路线 B，待评审后按第 5 节清单分步实施（先做「创建 PR」+「合并」两个最高频操作验证闭环）。
