1. **浅克隆导致 `git fetch upstream` 静默假同步**
   首次 `git fetch upstream --tags` 返回 0 且**无任何输出**，本地 `upstream/main` 仍停在 `01d7228b7e`（2026-09-04）；`git ls-remote upstream main` 显示远端实际已到 `b8f3b1ec00`。

3. **安装成功 ≠ 升级生效**

## 第二轮（用户反馈「版本为什么还是 197」）

### 用户问题
「当前版本 1.4.197-local.1789782638720.140117ca1732，我们的构建版本为什么还是 197，现在最新的版本应该是 205 了吧」

### 根因（不是代码没同步！）
`config/scripts/build-mac-local.mjs`：`version = createLocalBuildVersion(resolveVersionBase(packageJson.version), ...)`，而 `resolveVersionBase` = **max(package.json 版本, 本地最高纯 `vX.Y.Z` tag)**（`-rc.N` 会被正则过滤）。

1. **上游 main 的 package.json 长期是 `1.4.197`**，而远端发布 tag 已到 **`v1.4.206`**——`release: v1.4.206` 提交**不在 main 历史里**（发版走 release 分支 + tag：`.github/workflows/release-cut.yml` 的 `commit_message="release: v$VERSION"`）。⇒ 用 main 的 package.json 判断新鲜度是错的。
2. **本地 tag 过期**（浅克隆下 fetch 静默过期的同类现象）：本地最高只到 `v1.4.197` ⇒ 基数取到 1.4.197，代码最新但版本号看着旧。

### 处理
- `git ls-remote --tags upstream` 核对 → 远端最高纯版本 tag = **v1.4.206**（比用户预期的 205 还新一版）
- `git fetch upstream refs/tags/v1.4.206:refs/tags/v1.4.206` 补 tag（v1.4.198~205 未补，**不影响**基数——只补最高即可）
- 直接调用 `resolveVersionBase` 验证 → 输出 `1.4.206`
- **顺带追平上游最新 6 个提交**（`e2afb5eef9`）：合并提交 `b4d72ff19e`，1 个冲突 `usage-provider-contract.ts`（上游加 `'devin'`、二开有 `'zcode'/'pi'` ⇒ 取并集，顺便改成多行联合类型）
- 重跑流水线：`pnpm install`（+81 行锁文件）→ `pnpm tc` exit 0 → `verify-features` exit 0 → 重建安装
- **新版本：`1.4.206-local.1789785189109.117aa480069c`**（签名校验 exit 0）

### 决策：package.json 不动，版本基数交给 tag 机制
`package.json` 保持上游的 `1.4.197`（若改成 1.4.206，每次同步都会在版本行产生冲突）。⇒ **打包前应核对 `resolveVersionBase` 的输出 ≥ 远端最新发布 tag**。
