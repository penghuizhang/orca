### 关键事实（非显然）

1. **浅克隆导致 `git fetch upstream` 静默假同步**
   首次 `git fetch upstream --tags` 返回 0 且**无任何输出**，本地 `upstream/main` 仍停在 `01d7228b7e`（2026-09-04）；`git ls-remote upstream main` 显示远端实际已到 `b8f3b1ec00`。
   改用显式 refspec 强拉才更新：`git fetch upstream 'refs/heads/*:refs/remotes/upstream/*' --force` → 拿到 `7080eb0604`（2026-09-18）。
   **判据**：`git rev-parse --is-shallow-repository` = true；`.git/shallow` 有 10 条 graft（2026-08-15 ~ 09-03）。
   **纪律**：同步前必须核对 `git log -1 upstream/main` 的日期，不能只看 fetch 退出码。

2. **浅克隆让 main 分支无法合并上游（阻塞标准三步流程）**
   `git merge-base main upstream/main` 返回空（无共同祖先）→ `refusing to merge unrelated histories`。而 custom 与上游合并基正常（`01d7228b7e`）。⇒ 本次改为**直接 `custom merge upstream/main`**，main 未动。恢复标准流程需 `git fetch upstream --unshallow`（带宽成本高，待用户拍板）。
   附带事实：main 早已不是「纯净分支」——PR #19 把 custom 合进去过，且 main 是 custom 的祖先（custom 领先 main 105 个提交）。

3. **安装成功 ≠ 升级生效**
   `/Applications/orca-s.app` 已被替换为新版 `1.4.197-local.1789782638720.140117ca1732`，但**旧进程从 9/16 起一直在跑**（daemon 启动参数里仍是旧版本号 `...2c4e15b625e8`），`open` 只是激活旧实例（macOS 不替换运行中进程）。

### 经验 / 可复用
- **同步三步核对**：① `git ls-remote` 看远端真实 tip；② 显式 refspec 强拉；③ `git log -1 upstream/main` 核日期。浅克隆下缺任一步都可能「假同步」。
- **合并上游前先 `git merge-tree --write-tree` 预演冲突**，能提前知道冲突文件清单（本次预演 8 个 = 实际 8 个，零意外）。
- **打包版验收必须重启应用后再做**；「装好了」与「在跑新版」是两件事，用 daemon 启动参数里的 `--app-version` 判断实际运行版本最可靠。
- **提交合并前用 `git status --porcelain` + `verify-features` 双确认工作区**：未跟踪的会话产物会阻塞打包。
