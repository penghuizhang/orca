# 2026-10-20

## 需求

「拉取下远端代码，将代码进行合并推送到 custom 并从新打新的安装包」
= 拉上游 → 增量合并 → **直推 custom（非 PR）** → 重打 orca-s 安装包。

## 关键决策

1. **不重做上一轮**：HEAD 已是 `e7f4b1863f`（含上一轮 3010 提交的真 merge）⇒ 本轮只**增量合并** 578 提交。
2. **fetch 走 HTTPS+代理的带端口形式**：全局 `insteadOf` 把 HTTPS 改写回 SSH ⇒ `http.proxy` 失效、锁死 25KB/s；
   用 `https://github.com:443/...` 绕开前缀匹配 ⇒ 2.4MB/s（≈90×）。详见坑文件。
3. **冲突 9 处（预演 9 = 实际 9）**：6 语言包走脚本语义合并；生成物 `--fix` 重算；monaco 取**并集**；
   `store/index.ts` 取**上游新结构** + 注入二开 zcode/pi slice。
4. **11 处集成缺口全修**，其中 2 处**运行期破损**（zcode/pi 用量扫描、笔记外部路径授权），5 处自上一轮起就是错的；
   修法全部对齐上游同族实现（claude 的 sidecar 范式 / `extraRoots` 思路 / muse 的 schemaVersion 语义）。
5. **custom 直推**（用户明确要求）⇒ 取代上一轮的 PR #26。
6. **打包前置**：删冗余分支 `backup/sync-a87aa4ccdb-2c7cc68`（同提交另有 2 引用，零损失）；
   清 **93 个未跟踪 `.DS_Store`**（含撞死 buildId CRLF 校验的 `mobile/src/.DS_Store`）。

## 根因（本轮最有价值的三条）

1. **fetch 龟速真凶是 `insteadOf`**（不是浅克隆、不是对象量）：`GIT_CURL_VERBOSE` 零输出 = 根本没走 HTTP。
2. **上一轮记的「tc 通过」不成立**：上游本轮把 tc 默认编译器从 `native`(tsc) 改成 **bun** 且新增 bun devDependency，
   未装 bun 时 runner **直接抛错退出** ⇒ 旧结论里 node 项目其实从未真正通过（本轮单跑才首次看到那 5 处既有错误）。
3. **zcode/pi 用量扫描自上一轮起就是坏的**（运行期）：上游早已把 `scan` 第二参换成 `UsageSourceCacheRef` 对象，
   我方 scanner 在对象上 `.map()` ⇒ 必抛错 ⇒ 用量面板取不到数据；顺带发现 zcode「跳过未变更」会丢该库统计的既有隐患。

## 经验（重踩检测）

- **重踩**：`.DS_Store` 撞 buildId 校验（已记过）⇒ 新约束：**打包前先 `find . -name .DS_Store` 清一遍**，别等构建报错。
- **新认知**：验证类结论有**工具链时效性**——同一句 `pnpm tc` 在不同上游版本下检查范围可能不同（编译器默认值会变），
  所以**历史验证结论要当「待复核」而非事实**；tc 必须看到「四项目各自 ✓」才算过。
