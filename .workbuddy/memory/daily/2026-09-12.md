### 根因（一句话）
zustand v5 下 selector 返回新对象 ⇒ `useSyncExternalStore` snapshot 不稳定 ⇒ React nested update 超 50 ⇒ minified React error #185；状态栏因常驻挂载必然命中，另 3 处同源消费者（ports 弹层 / 侧栏工作区端口行 / 右侧栏 Ports 面板）在各自挂载时才命中。

### 经验 / 蒸馏
- **打包版崩溃别猜、别硬复现**：`~/Library/Application Support/<productName>/crash-reports.json` 里已含 `boundary_id` + `error_message` + `component_stack`，是定位渲染期崩溃最快的一手证据。productName 为 `orca-s`（本 fork 打包名）。
- **React #185 的 `component_stack` 只能当线索**：nested-update 计数器是模块级全局的，报错的组件多半是「恰好被选中的当事者」（`attribution: unreliable`），真正定位要靠「哪个 selector/dep 引用不稳定」。
- **zustand v5 高危写法**：selector 内构造对象/数组。仓库已有 92 处 `useShallow` 正确示范，可作为巡检依据。
- 上游 `git fetch upstream` 慢/超时，但**按需取单个文件/commit 可用** `curl --proxy http://127.0.0.1:54687 https://raw.githubusercontent.com/stablyai/orca/<sha>/<path>` 与 GitHub API（`/commits?path=...` 反查引入点与修复点，省大量代码考古时间）。
