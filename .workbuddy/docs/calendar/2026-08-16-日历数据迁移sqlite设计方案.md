# 二开业务库 orca-custom.db 设计与日历数据迁移方案

日期：2026-08-16
状态：待评审
分支：feature/calendar-sqlite → custom（PR）

## 1. 背景与目标

用户决策：
1. 二开功能的数据**不复用 Orca 原生库**（orchestration.db 等），单独建一个**二开专属业务库**；
2. 接口直接用原生 `node:sqlite`（DatabaseSync），不依赖上游封装；
3. 该库是**通用业务库**，不只日历——后续日志等其他二开功能也往里面加表；
4. 库名定为 **`orca-custom.db`**，路径 `<userData>/orca-custom.db`。

目标：建立通用业务库骨架（建库 + 版本迁移 + 业务表注册），日历条目作为**第一张业务表**迁入，renderer/IPC 零感知，历史数据自动迁移，并回退对上游文件（persisted-state-types.ts / constants.ts）的自定义字段。

## 2. 现状调研结论（与上一版一致，摘要）

- 日历条目现存在 `<userData>/orca-data.json` 的 `calendarEntries` 字段，消费点集中在 main 进程 Store（persistence.ts 5 个方法）+ IPC + preload，renderer 全走 IPC → 改动可完全收敛 main 进程。
- Orca 原生 sqlite 用 Node 内置 `node:sqlite`（Electron 43 可用，orchestration.db 生产验证）；无 better-sqlite3 native 打包问题。
- orchestration.db 不复用（上游文件 + 专属 SCHEMA_VERSION v28 迁移体系 + 语义专属）。
- Store 加载为 `JSON.parse as PersistedState` 纯断言：移除字段后旧 JSON 多余字段自然忽略（已验证 persistence.ts:3213）。

## 3. 通用业务库设计

### 3.1 目录与文件

```
src/main/custom-db/
  custom-db.ts          # 库入口：打开/建库、schema 版本迁移、文件权限硬化
  calendar-table.ts     # 业务表 1：calendar_entries（日历条目 CRUD）
  custom-db.test.ts     # 迁移机制 + 通用性测试
  calendar-table.test.ts
```

### 3.2 `custom-db.ts`：库骨架（通用，业务无关）

- 打开 `<userData>/orca-custom.db`：直接用 `node:sqlite` 的 `DatabaseSync`（用户允许用原生接口），构造时设 pragma `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`（对齐原生库的做法）。
- **迁移机制（通用）**：`MIGRATIONS: readonly Migration[]`，每条 `{ version: number, up: (db) => void }`；`PRAGMA user_version` 记录当前版本；启动时从当前版本逐条执行到最新，迁移全部包在一个事务里（失败回滚 user_version，下次重试）。版本从 1 起。
- **表注册**：迁移即注册——新增业务功能 = 在 MIGRATIONS 追加一条 `CREATE TABLE IF NOT EXISTS …`。日历是 v1。
- 文件权限硬化：参考原生 orchestration 的做法，POSIX 下对 db/-wal/-shm chmod 0o600（Windows 跳过）。
- `close()`：关闭 DatabaseSync。

### 3.3 `calendar-table.ts`：日历业务表（v1 迁移）

```sql
CREATE TABLE IF NOT EXISTS calendar_entries (
  id            TEXT PRIMARY KEY,
  title         TEXT NOT NULL DEFAULT '',
  date          TEXT NOT NULL,            -- YYYY-MM-DD 本地日历日
  all_day       INTEGER NOT NULL DEFAULT 0,
  start_time    TEXT,                     -- HH:mm，null=全天
  end_time      TEXT,
  category      TEXT NOT NULL DEFAULT 'other'
    CHECK(category IN ('meeting','feature','milestone','other')),
  description   TEXT NOT NULL DEFAULT '',
  lunar_repeat  TEXT,                     -- JSON {"month":m,"day":d}，null=无
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_calendar_entries_date ON calendar_entries(date);
```

- 方法：`list()` / `create(input)` / `update(id, updates)` / `delete(id)`。
- **校验与排序复用 shared 层**：`normalizeCalendarEntry` / `applyCalendarEntryUpdate` / `compareCalendarEntriesByStart`——list 先 SQL 取行再 JS 规范化+排序，行为与现状一致；非法行按现状语义丢弃（normalize 返回 null）；create 的 normalize 失败仍抛 Error（与现状 store.createCalendarEntry 一致）。
- `lunar_repeat`：`isCalendarLunarRepeat` 校验后 JSON 序列化入库；读回经 normalizeCalendarEntry 反序列化校验。
- `id`：`randomUUID()`（与现状一致）。

### 3.4 Store（persistence.ts）改造

- Store 构造时打开 `CustomDb`（路径复用 `initDataPath` 后的 userData 目录）；Store 关闭路径追加 `customDb.close()`。
- 5 个日历方法改为委托 `CalendarTable`；`state.calendarEntries` 从 PersistedState 移除（回退 persisted-state-types.ts 与 constants.ts:453 的改动）。
- 遗留迁移 `migrateLegacyCalendarEntries()`（Store load 后执行一次）：
  1. `state.calendarEntries` 空/undefined → 跳过（幂等）；
  2. 非空 → 逐条 normalize + `INSERT OR IGNORE`（id 主键防重复）；
  3. 全部成功 → `state.calendarEntries = undefined` + 持久化一次（清 JSON 旧字段）；
  4. 任一条失败 → 保留 JSON 字段 + 日志，下次启动重试，不阻塞启动。

### 3.5 不改的部分

- IPC / preload / renderer 全部组件：接口不变，零感知。
- 历法常量（holiday-data.ts / solar-term.ts）：仍代码内置。
- 远程/web 模式：calendar IPC 仅桌面 main 注册，无远端路径。

### 3.6 未来扩展（设计承诺）

- 新二开功能（如日志）：在 `src/main/custom-db/` 加对应 `*-table.ts` + MIGRATIONS 追加 vN 建表，业务逻辑自持，互不干扰。
- 库是单一文件，备份随 userData 目录即可整体覆盖。

## 4. 收益与代价

**收益**
- 二开数据独立成库：不依赖上游库 schema 演进、不被上游清理逻辑误伤；上游 sync 冲突面减小（回退 2 个上游文件的自定义字段）
- 通用骨架：后续功能加表即用，无需重复搭迁移/权限/打开逻辑
- 数据可 SQL 查询，未来按日期范围/分类统计直接可用

**代价/风险**
- 新增 ~300 行（骨架 + 日历表 + 迁移 + Store 委托 + 测试）
- orca-data.json 的备份轮转/云 profile 机制不含 calendar 数据（迁库后日历数据以 orca-custom.db 为唯一副本；个人数据量小，风险低；如后续用云 profile 需另议）
- node:sqlite 依赖 Electron 内置 Node ≥22.5（Electron 43 满足，原生库已生产验证）

**诚实评估**：JSON 对个人日历数据量完全够用，但独立业务库的收益（sync 解耦 + 通用扩展骨架）对二开项目是实打实的，推荐做。

## 5. 验收标准

1. 新建日历条目 → 落在 `<userData>/orca-custom.db`（sqlite3 CLI 可查 calendar_entries 表），orca-data.json 无 calendarEntries
2. 旧数据自动迁入且 JSON 字段清除；重复启动不重复迁移；迁移失败保留 JSON 字段
3. 日历 UI 增删改查与迁移前行为一致（回归单测 + 手动验收）
4. typecheck 三套 + 相关单测全绿；verify:localization-catalog 通过
5. 打包版（orca-s）验证 db 路径在 `Application Support/orca-s/orca-custom.db`
6. 迁移机制可扩展：测试里验证「追加 v2 迁移 → 旧库自动升级 user_version」的通用性

## 6. 约束清单（实施自查）

- 【约束】renderer/preload/IPC 接口零改动（改动收敛 main 进程）
- 【约束】库名 orca-custom.db，路径随 userData；不复用/不修改 orchestration.db 及 sync-database.ts
- 【约束】接口用原生 node:sqlite（DatabaseSync），不依赖上游封装
- 【约束】迁移机制通用：user_version 跟踪 + 事务 + 失败回滚；业务表经 MIGRATIONS 注册
- 【约束】校验/排序复用 shared 层 normalize/apply/compare，不复制逻辑
- 【约束】遗留迁移幂等（INSERT OR IGNORE + id 主键）、失败保留 JSON 字段不丢数据
- 【约束】不新增 max-lines disable；大 JSON 提交后 json.load 验证
- 【约束】功能走 feature/calendar-sqlite → PR → custom
- 【约束】实施前备份当前 orca-data.json（防迁移逻辑翻车丢数据）
