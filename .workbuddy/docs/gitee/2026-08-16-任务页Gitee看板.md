# 任务页 Gitee 看板:入口可见性修复

日期:2026-08-16 | 分支:gitee-integration | 类型:精简设计说明(小修复)

## 需求(用户原话转写)

截图(红框框选左侧「任务」页签,红字批注「添加gitee相关的功能,功能内容和github的相同」):
- 任务页点开后,添加一个「Get 议题」(= Gitee 议题)看板;现在已有「Get Help」(= GitHub)的。
- 点击后显示的内容(议题、PR 等)与 GitHub 完全相同即可。

## 现状分析(已确认)

- **L2-B(commit 78c91d516)已实现全部功能**:TaskPage 任务来源图标条已含 Gitee(`getSourceOptions` 5 项)、Gitee 视图(Pull requests / Issues 两个页签 + 账号级聚合列表 + 刷新)已渲染、侧边栏「任务」hover 图标组已加 Gitee(ce2d89874)。
- **根因:用户持久化设置缺 `gitee`**。实测用户数据 `~/Library/Application Support/orca-dev/profiles/local-default/orca-data.json`:
  `settings.visibleTaskProviders = ["github","gitlab","linear","jira"]`(保存于 Gitee 加入之前)。
  `normalizeVisibleTaskProviders` 只做去重/过滤、**从不追加缺失 provider** → 任务页头部来源图标条(`visibleSourceOptions` 按 visibleTaskProviders 过滤)与侧边栏 hover 图标(`visibleTaskProviders.includes('gitee')`)都不显示 Gitee → 用户无法进入 Gitee 看板。
- **上游已有同类迁移模式**:Jira 加入时用一次性迁移 `visibleTaskProvidersDefaultedForJira`(persistence.ts 加载时若 flag 未置位且列表缺 jira 则追加,保存时盖章),本修复完全照搬该模式。

## 方案

在持久化层加 Gitee 一次性可见性迁移(4 处镜像 jira):

| 文件 | 改动 |
|------|------|
| `src/shared/global-settings-types.ts` | 新增字段 `visibleTaskProvidersDefaultedForGitee: boolean` |
| `src/shared/constants.ts` | 默认值 `visibleTaskProvidersDefaultedForGitee: true`(新 profile 全量可见,无需迁移) |
| `src/main/persistence.ts` | ① 加载迁移:flag 未置位且列表缺 `gitee` → 追加(参照 3428-3436 jira 链);② flag 未置位 → `loadNeedsSave = true`;③ 全量保存盖章(参照 3642);④ 部分更新(`'visibleTaskProviders' in updates`)盖章(参照 6178) |
| `src/main/persistence-source-control-ai-migration.test.ts` | 更新 2 个现有用例预期 + 新增 gitee 迁移用例(镜像 jira 测试) |

不改 renderer:迁移在主进程持久化加载时完成,渲染层拿到的 settings 已含 gitee。

## 约束清单(实施自查)

1. 【约束】迁移只追加、不删除;用户后续手动隐藏 gitee 后不得再被加回(flag 盖章即一次性)。
2. 【约束】jira 迁移链不动,两个迁移叠加时结果正确(先 jira 后 gitee)。
3. 【约束】新 profile 默认值 `visibleTaskProviders` 已含 gitee(常量 `TASK_PROVIDERS`),flag 默认 true 不触发迁移。
4. 【约束】加载迁移必须置 `loadNeedsSave`,保证落盘盖章。
5. 【约束】不新增 i18n key、不动 TaskPage 渲染逻辑(入口已存在,只是被设置挡住)。
6. 【约束】改完三个 typecheck(node/web/cli)+ 相关单测 + oxlint 全绿;main 进程改动需重启 dev 才生效。

## 验收路径

重启 dev → 任务页头部图标条出现 Gitee(文件夹图标)→ 点击进入看板 → Pull requests / Issues 页签显示账号级聚合列表,与 GitHub 看板内容形态一致。

## 风险

- 该迁移会让**所有**存量 profile 自动显示 Gitee 入口(含曾主动隐藏者一次);与 jira 迁移行为一致,可接受。
- 不改 Gitee 看板本身(已有的 PR/议题视图即满足「内容与 GitHub 相同」);若后续要 Gitee 项目看板/按仓库视图,另立任务。

## Gitee API v5 能力分析(2026-08-16 晚,swagger 全量拉取 175 端点)

### 数据管道对比(GitHub vs Gitee)
- GitHub:TaskPage → window.api.gh.* → main/github/client.ts → **gh CLI**(gh api search/issues、gh pr list --search --json)→ 服务端搜索语法(is:issue/assignee:/label:/review-requested:)+ rich WorkItem 模型。
- Gitee:TaskPage → window.api.gitee.* → main/gitee/client.ts → **HTTP REST**(fetch + PAT)。

### 实测结论
- `/search/issues?q=` **只支持全文搜索**,repo:/state:/is:/label:/assignee: qualifiers **全部不生效**(400 或按相关性全文返回)→ 结构化过滤只能本地做(已实现)。
- 端点能力远超当前使用(175 个):merge、review、assignees、labels CRUD、milestones、comments、commits/files、check-runs、user、enterprises、collaborators 全都有。

### 能力矩阵(1:1 可行性)

| GitHub 功能 | Gitee API 对应端点 | 状态 |
|---|---|---|
| Issue/PR 列表 | GET /repos/{o}/{r}/issues、/pulls | ✅ 已做 |
| 账号级聚合 | /user/repos + 按仓库聚合 | ✅ 已做 |
| 搜索(全文) | /search/issues?q= | ⚠️ 服务端全文+本地结构化过滤 |
| 标签展示/管理 | issues/{n}/labels、pulls/{n}/labels CRUD | ✅ 展示已做;管理待做 |
| 里程碑(≈项目页签) | /repos/{o}/{r}/milestones CRUD | ⏳ 可做 |
| 评论 | issues/{n}/comments、pulls/{n}/comments GET/POST | ⏳ 详情对话框 |
| PR commits/files | pulls/{n}/commits、/files | ⏳ 详情对话框 |
| 评审人列+操作 | pulls/{n}/assignees、/review | ⏳ PR 管理列 |
| 合并 PR | GET/PUT pulls/{n}/merge | ⏳ PR 管理列 |
| CI 检查 | commits/{ref}/check-runs | ⚠️ 需实测 |
| 创建 Issue/PR | POST /repos/{o}/{r}/issues、/pulls | ⏳ 可做 |
| 「分配给我」筛选 | GET /user(login) | ⏳ 可做 |
| 详情对话框 | 上述组合 | ⏳ Gitee 版 GitHubItemDialog |

### 结论:1:1 路径 = 桥接层
- 数据层:扩展 gitee client 覆盖上表端点;字段映射成 WorkItem 形状
- UI 层:复用 GitHub 分支渲染(页签/筛选/搜索/列/行);GitHub 特有列(checks)按数据有无显隐
- 分阶段:① 形态 1:1(基本完成)② 详情对话框 ③ PR 操作(合并/审查/标签)④ 里程碑/创建/分配给我
- 明确不可 1:1:GitHub 服务端搜索 qualifiers、GraphQL、CI checks 完整管线
