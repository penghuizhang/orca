## 1. 背景与目标

用户代码主要托管在 Gitee（GitHub 网络受限）。目标：Orca 对 Gitee 仓库提供与 GitHub/GitLab 对等的集成能力。

## 2. 现状调研（关键结论：Orca 已是多 provider 架构，Gitee 有现成范式可循）

### 2.1 forge 抽象层

- `src/main/source-control/forge-provider.ts` 定义统一接口 `ForgeProvider`（id / supportsReviewCreation / resolveRepository / getReviewForBranch / getReviewByNumber / createReview），注册表 `FORGE_PROVIDERS` 现有 **5 个 provider**：GitLab、GitHub、Bitbucket、Azure DevOps、Gitea（forge-provider.ts:296-299）。
- Provider 判定：`getForgeProviderForRepository` 按注册表顺序逐个调 `resolveRepository` 探测（forge-provider.ts:309-317）；未命中返回 `unsupported`（:320-323）。**新增 provider = 加一个实现 + 注册一行，判定链不用动。**

### 2.2 各 provider 实现模式（认证方式各不相同，可选参照）

| Provider | 目录 | 认证/API 方式 | 规模 |
|---|---|---|---|
| GitHub | src/main/github/ | `gh` CLI（ghExecFileAsync / `gh api`，client.ts:56-57,430） | client.ts 5581 行 + 大量子模块 |
| GitLab | src/main/gitlab/ | `glab` CLI（client.ts:102 `auth status`） | ~40 文件 |
| Gitea | src/main/gitea/ | HTTP 直连 + remote-ref 探测；`KNOWN_NON_GITEA_HOSTS` 排除已知平台（repository-ref.ts:17-22） | 9 文件 |
| Bitbucket | src/main/bitbucket/ | HTTP + 自有 credential-store / resolve-auth（credential-store.ts, resolve-auth.ts, bitbucket-auth-config.ts） | 15 文件 |
| Azure DevOps | src/main/azure-devops/ | HTTP（azure-devops-api-request.ts） | 10 文件 |

### 2.3 接线面（GitLab 全套接线清单 = Gitee 要照抄的接线面）

- IPC 层：src/main/ipc/gitlab-repo-access.ts、gitlab-issue-handlers.ts、gitlab-merge-request-mutation-handlers.ts、gitlab-work-item-handlers.ts、gitlab-ci-job-handlers.ts，注册于 register-core-handlers.ts
- RPC 层：src/main/runtime/rpc/methods/gitlab.ts（挂载于 index.ts）
- 运行时：src/main/runtime/orca-runtime.ts、runtime-rpc.ts、selected-review-branch.ts 等引用
- 渲染层：GitLabItemDialog.tsx（对应 GitHubItemDialog.tsx）、PullRequestPage.tsx、store/slices/github.ts 等
- 共享类型：src/shared/hosted-review.ts（HostedReviewProvider 联合类型，新增 provider 需扩此类型）

### 2.4 远端识别

- `src/shared/git-remote-identity.ts` 是 host 无关的通用解析（host/path/SSH alias）
- provider 归属由各 provider 的 `resolveRepository` 自行探测（如 Gitea 用 remote-ref 探测 + 排除表）；Gitee 需同类实现

## 3. Gitee API 与认证形态（2026-08-16 实测）

- API：Gitee OpenAPI v5，基址 `https://gitee.com/api/v5`，REST 风格、响应结构与 GitHub API v3 高度相似
- 实测（公开只读，无需 token）：`GET /api/v5/repos/{owner}/{repo}` 返回仓库信息 ✓；`GET /api/v5/repos/{owner}/{repo}/pulls?state=open` 返回 PR 列表 ✓
- 认证：OAuth2 授权码流（官方文档指向 authorization endpoint, response_type=code）+ **私人令牌 private_token**（Gitee 特色：可带 query 参数或 header）
- **Gitee 没有官方 CLI**（gh/glab 模式不可用）→ 认证与 API 必须走 HTTP + token 模式，参照 Bitbucket（credential-store）或 Gitea（HTTP 直连）
- 私有化/企业版：Gitee 有企业版（gitee.com 内企业路径）与私有化部署（gitee-enterprise），本方案先只支持 gitee.com 公有站，私有化留扩展位

## 4. 分级方案（建议按 L0 → L1 → L2 推进，每级可独立交付）

### L0：基础可用（git 层 + 远端识别）— 改动最小，建议必做

现状：**git clone/push/pull/终端对 gitee.com 已可用**（git 不挑远端），但 Orca 会把 Gitee 仓库判为 `unsupported` provider，PR/评审类 UI 与图标识别等降级。

改动（全部为新增文件 + 注册表一行追加，冲突面极小）：

1. `src/main/gitee/repository-ref.ts`：gitee.com host 解析（owner/repo/apiBaseUrl/webBaseUrl），仿 src/main/gitea/repository-ref.ts
2. `src/main/gitee/forge-provider.ts` 或并入：实现 `ForgeProvider.resolveRepository`（识别 gitee.com）
3. forge-provider.ts:296-299 注册表追加 `giteeForgeProvider`
4. src/shared/hosted-review.ts 的 `HostedReviewProvider` 联合类型加 `'gitee'`；reviewLinkForProvider（hosted-review.ts:20-36）加 case
5. src/main/repo-icon-autodetect.ts 加 gitee.com 图标识别（该文件已引用 gitlab/gitea）

验收：在 Orca 中打开 gitee.com 仓库，provider 识别为 gitee，PR 相关入口不再报 unsupported。

### L1：PR/Issue 只读浏览 + 认证 — 主价值层

1. 认证：私人令牌（PAT）输入/存储，仿 `src/main/bitbucket/credential-store.ts` + resolve-auth；渲染层加设置入口（参照 Bitbucket/GitLab 的认证 UI 位置）
2. API 客户端：`src/main/gitee/client.ts` 实现 list pulls / get pull / list issues / get user 等只读方法（Gitee v5 与 GitHub v3 结构相近，可参考 github/client.ts 的字段映射但**不要**复用 gh CLI 路径）
3. 只读接线：PR/Issue 列表与详情在渲染层展示（新 GiteeItemDialog 或复用通用面板），IPC 注册只读 handlers（仿 ipc/gitlab-issue-handlers.ts 最小集）
4. 工作量估计：约 1-2 周（含认证 UI + 测试），主要成本在渲染层接线与测试

### L2：创建 PR、评审注释、CI 状态等深度功能 — 按需再议

对标 gitlab 的 merge-request-creation、mr-review-actions、pipeline-job-graph 等；Gitee 均提供对应 API（pulls 创建、review_comments、webhooks/CI），但这是大工程量，建议 L1 落地后按真实使用反馈再排。

## 5. 影响面与风险（约束清单，实施时逐条自查）

- 【约束1】改动以「新增文件为主」：新增 src/main/gitee/、src/renderer 新组件；只改 forge-provider.ts 注册表、shared/hosted-review.ts 类型、hosted-review.ts switch 三处既有文件 → 与上游日更 merge 的冲突面收敛到这三处（上游也常改 forge-provider.ts，冲突概率中等，逐文件 resolve 即可）

- 【约束3】不破坏既有 provider 判定：Gitee resolveRepository 必须用「host 匹配 + remote-ref 探针」双确认，避免把 github/gitlab 仓库误判（参照 gitea 的 KNOWN_NON_GITEA_HOSTS 排除表思路）
- 【约束4】API 字段以实测为准：Gitee v5 与 GitHub v3 相似但不相同（如 Gitee 的 pulls 结构缺部分字段），实施时逐接口对照 https://gitee.com/api/v5/swagger 验证，不凭 GitHub 结构猜测
- 【约束5】测试对齐仓库规范：新增文件需配套测试（仓库 52% 行数是测试，oxlint + max-lines-ratchet 门禁在 CI）
- 【约束6】远程/SSH 场景：resolveRepository 与 client 调用需走既有 connectionId 路由（probeGitRemoteIdentity 已支持，repo-git-remote-identity.ts:16-19）

## 7. 结论

Orca 的多 provider 架构（5 个现有 provider + 统一 ForgeProvider 接口）使 Gitee 集成有**明确的照抄范式**，无架构性障碍；Gitee API v5 形态与 GitHub v3 相近且公开接口实测可用。总工作量取决于范围：L0 ≈ 1 天，L0+L1 ≈ 1-2 周。风险主要在上游日更对 forge-provider.ts 的并发修改与 Gitee API 字段差异，均有对策。
