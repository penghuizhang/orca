## 0. TL;DR

研发云（www.srdcloud.cn）是**天翼云 EasyCoding 产品线的企业内网部署**（内部 DNS 解析到 10.158.x.x），不是普通 SaaS。平台没有公开 OpenAPI 文档、没有面向第三方的 PAT 体系，全站多套 SSO 登录墙——**但这不是阻断点**：

- **git 托管 = Gerrit 2.13**（code.srdcloud.cn），有标准公开 REST API；
- **代码中心 = 完整 GitHub 对等体**：383 个网关 API 端点（PR/分支/提交/文件/评审/保护分支/回收站），走 `/api/codebackend`；
- **工作项（Bug/需求） = 独立后端**（/zte-rdcloud-rdc-* 路径），自带头鉴权（X-Emp-No/X-Auth-Value），UAC SSO；
- 平台自身 AI 助手 CodeFree = 改装版 opencode（本机 `codefree-o` CLI 就是它），走 acbackend 网关 + apiKey/userId/sessionId 自定义头——**已确认平台存在 API key 管理能力**（`/api/acbackend/usermanager/v1/users/apikey`）。

集成路径与 Gitee 完全同构（独立模块 + 注册表接线 + 独立 UI 的 copy 路线），且**上游日更 66 commits 永远不会碰 srdcloud 代码，冲突面比 Gitee 还小**。工作量分级：L0 识别 ≈ 1 天；L1（认证 + 工作项/PR 只读）≈ 2-3 周；L2（Gerrit 评审操作、工作项操作、CI/制品浏览）按需排期。

## 1. 需求与背景

用户（中国电信，devops@chinatelecom.cn）要把公司研发云平台集成进 Orca，目标：
1. **免登录直接查看代码库、代码提交、Bug**（工作项）——原调研（已暂停）的核心诉求；
2. 按 Gitee 集成的方式集成（照抄接线模式）；
3. **研发云会比 Gitee 集成得更多**——平台是全链路 DevOps：代码、评审、工作项、CI、制品、部署、测试、度量、文档。

### 2.2 git 托管：Gerrit（重大发现）

- **code.srdcloud.cn = Gerrit Code Review 2.13.9-CCM-20200428**（`/config/server/version` 免登录 200）
- `/a/accounts/self`、`/login/` → 302 到 www.srdcloud.cn（SSO 门户会话）；HTTP Basic 无效（302 不 401）→ **Gerrit 只认门户 SSO 会话**
- 平台提供 Gerrit 桥接：代码中心 API 有 `app-inf/v1/queryUserGerritLoginInfo`（查用户 Gerrit HTTP 密码）、`auth/v1/addUserSsh|getSshKeys|delUserSshKey`（SSH 密钥管理）——**git 认证有官方通道**

### 2.4 工作项（Bug/需求/任务）—— 用户核心诉求

- 应用 zxwim（工作项应用），独立 SPA（/wim/），后端路径不走 /api 网关前缀，而是：
  - `/zte-rdcloud-rdc-rdcserver/rdc/...`（主 API，config: `VUE_APP_API`）
  - `/zte-rdcloud-rdc-wimbackend/wic/api/workspaces/{ws}/work_items/...`（视图/查询/编辑/批量状态）
  - `/zte-plm-wic-api`、`/zte-plm-wic-rest`（WIC 配置）
- 数据模型：**workspace（工作空间=项目/团队）→ work_items（工作项：Bug/需求/任务）→ view_queries（视图/筛选）→ fields（字段）**；支持迭代（IterationPath）、区域（AreaPath）、团队（Team）、StoryPoints
- 实测免登录调用返回：`{"code":{"code":"0002","msg":"HTTP Header \`X-Emp-No\` or \`X-Auth-Value\` is null."}}`——**鉴权 = X-Emp-No（工号）+ X-Auth-Value（UAC token）+ X-Lang-Id 自定义头**
- SSO：中兴 UAC（`uactest.zte.com.cn/portal/login.html?businessSystemCode=100000462184`，另有 i.zte.com.cn 引用），config 环境=beta（`VUE_APP_ENV: 'beta'`）

## 4. 研发云 vs Gitee 的差异（决定方案要点）

1. **不是单一 forge，是 DevOps 全家桶**：git(Gerrit) + 代码中心(383 端点) + 工作项 + CI + 制品 + 文档。forge provider 只是入口之一；TaskProvider 'srdcloud' 聚合工作项 + PR。
2. **双后端双鉴权**：codebackend 走门户会话；工作项走 X-Emp-No/X-Auth-Value。Orca 需要同时持有两套（或确认门户会话能单向打通——实现期用真实会话验证）。
3. **内网可达性**：DNS 解析到 10.158.x.x，只有企业内网/VPN 可用。**SSH 远程工作区（AGENTS.md SSH 用例）在远端主机上不可用**——集成必须优雅降级（远端仓库识别为 srdcloud 但查询报「内网不可达」）。git 操作走用户本机 origin remote 配置。
4. **无公开 API 文档**：字段映射以实测/前端 bundle 为准（与 Gitee swagger 175 端点对照同思路，但来源是前端 JS）。
5. **Gerrit 2.13 老旧**：REST API 能力有限（无 GraphQL、无搜索 qualifiers、无 check-runs），PR 概念在 Gerrit 是 change/review；平台代码中心 prreq/v1 把 Gerrit 包装成了 GitHub 式 PR——**优先用代码中心 prreq API，不直连 Gerrit REST**（后者只用于 git 传输）。
6. **平台自身在迭代**（config env=beta、内部版本号 Internal）：接口可能变动；实现时给 client 层统一错误分类 + 字段可选降级。

## 5. 分级方案

### L0：远端识别 + provider 接线（≈1 天，建议必做）

1. `src/main/srdcloud/repository-ref.ts`：解析 `https://code.srdcloud.cn/{project}`、`ssh://...`、`www.srdcloud.cn` 形态（**Gerrit 单段 project 名**，含 Gerrit 特有 refs/for/ 检出形态）；SSH alias 处理
2. `srdcloud/forge-provider.ts` + forge-provider.ts 注册表追加（supportsReviewCreation=false）
3. shared/hosted-review.ts 联合类型 + reviewLinkForProvider + 全部穷举 switch 占位（照 Gitee L0 提交 8a8060133 模式）
4. repo-icon-autodetect.ts 图标识别
5. 测试：repository-ref 单测（拒绝 github/gitee/gitlab/自托管 host）、forge-provider.test.ts 预期表追加

### L1：认证 + 工作项/PR/提交只读浏览（≈2-3 周，主价值层）

1. **认证**：Settings → Review providers 加「研发云」卡片；**分层凭证策略（第 8 节）**——git 走 Gerrit HTTP Password（长期），API 走门户/工作项 token + 一键 OAuth 重登；safeStorage 加密存储 + env 优先（ORCA_SRDCLOUD_TOKEN）；connect 时验证（调一个轻量只读端点）
2. **client.ts**：requestSrdJson（codebackend）+ requestWimJson（工作项，X-Emp-No/X-Auth-Value 头注入）；工作项列表按 workspace 聚合
3. **IPC**：connect/disconnect/status + listRepos（代码中心 repositoryList）+ listWorkItems（工作项，按 workspace/view）+ listPulls（prreqlist）+ listCommits（gitweb commit-history）+ itemDetail
4. **UI**：**独立页签 SrdcloudWorkspacePage**（第 7 节形态：连接状态卡片 + 工作项/仓库/PR 页签，TopLevelView 'srdcloud' 照日历模式）+ SrdItemDialog（工作项/PR 详情）+ Settings 连接卡片（token 管理/有效期显示/一键重登，第 8 节）
5. **linkedSrdcloudPR / linkedSrdcloudWorkItem 元数据**接线（worktree 卡片显示关联 PR/工作项，照 linkedGiteaPR 模式）
6. i18n：en 由 sync 自动补，zh/es/ja/ko 手工补
7. 可见性迁移 visibleTaskProvidersDefaultedForSrdcloud

### L2：深度功能（按需排期，用户拍板范围）

- Gerrit 评审操作：提交评审（refs/for/）、code review +2/-2（需 Gerrit 会话通道确认）、评审意见
- 工作项操作：创建/编辑/状态流转/指派（wic work_items edit 端点已在 bundle 中确认存在）
- 代码浏览：Orca 内嵌树/文件/提交 diff（gitweb/v1、commit-diff）
- 提交↔工作项关联展示（management-backend getCommitMessageRelatedWorkItem）
- CI 状态（集成中心 /api/cibackend）、制品浏览（Artifactory REST 公开标准）、AI 评审结果展示（aireview/v1）
- OAuth2 授权码登录（需平台开放 client 注册——**目前无证据平台支持**，列为长线）

### 明确不可做（与 Gitee 同结论）

- 服务端搜索 qualifiers（Gerrit/代码中心无对等物）→ 本地过滤
- GraphQL（无）
- 无平台开放平台（open API 文档/第三方 PAT）之前，不做「平台内嵌应用市场」类集成

## 8. 认证与 token 生命周期（用户追问 2026-08-16 深夜）

**用户痛点确认（实测证据）**：本机 `~/.codefree-cli/oauth_creds.json` 显示平台 OAuth 签发：`access_token`（uuid 格式）+ `expires_in=86400`（**24 小时**）+ `token_type=bearer` + **`refresh_token_expires_in=0`（平台不签发 refresh token）**。→ 「每天都要登录」是平台强制的，不是 Orca 或用户操作问题。

### 分层凭证策略（推荐组合，按通道选最长效凭证）

| 通道 | 凭证 | 有效期 | 策略 |
|---|---|---|---|
| git（Gerrit HTTPS） | **Gerrit HTTP Password**（用户 Gerrit 设置自助生成，或 app-inf/queryUserGerritLoginInfo） | **长期**（直到用户重置） | safeStorage 加密存 + 写 git credential helper → **git 通道一次生成长期稳定，无每日登录** |
| 代码中心 API（/api/codebackend） | 门户 access_token | 24h | 加密存 + 过期检测 + 自动重登 |
| 工作项 API（X-Auth-Value） | UAC token | 短 | 同上 |
| AI 服务（acbackend） | apiKey + sessionId | 疑长期（待确认） | 若实测 DevOps 服务也认 → 优先做长期通道 |

### 过期处理三级策略

1. **一级（推荐先做）——一键 OAuth 重登**：Orca 点「重新连接」→ 系统浏览器打开平台 SSO（open.e.189.cn / UAC）→ 授权后回跳 localhost → 自动收 token 并加密落盘。用户每天过期后**点一次、5 秒完成、不手输任何东西**。比现在「每天手动登录」体验质变。
2. **二级——后台自动续期**：若实测发现平台某通道支持长效凭证（acbackend apikey 对 DevOps 服务可用、或 UAC 有 app token、或未来平台开放 refresh_token），则启动时/调用前静默换新，用户完全无感。**现状证据（refresh_token_expires_in=0）不支持**，列为「实测确认后升级」。
3. **三级——平台侧申请**：走公司流程向平台方申请企业 API 凭证/开放 refresh_token。最正规但时间不可控，作为长期解并行推进（用户在电信内部，可找研发云平台组提需求）。

### token 安全限制（能做什么限制）

- 所有凭证存本机 safeStorage 加密（复用 integration-credential-file 机制，同 Gitee PAT），**不进日志、不进聊天记录、不进 git**
- env 变量注入优先（ORCA_SRDCLOUD_TOKEN 等，CI/无头场景）
- token 最小权限：若平台支持子服务 key 用最小范围；不支持则至少按通道分存（门户/工作项/gerrit 密码各自独立，失效互不影响）
- 连接卡片显示各凭证有效期，失效前提醒

### 待实测确认（L1 开工后第一件事）

1. 门户 OAuth 完整响应结构（用用户真实浏览器会话抓包：是否有 refresh_token、cookie 名、网关接受的头名）——决定一级还是二级
2. acbackend apikey 能否覆盖 DevOps 服务（平台侧确认 or 实测）
3. Gerrit HTTP password 自助生成路径验证（标准 Gerrit: Settings → HTTP Credentials）

## 9. 待用户拍板的决策点

1. **范围**：L0 单独做（1 天）还是 L0+L1 一起（2-3 周）？L2 哪些项排期？
2. **入口形态**：确认走独立页签（第 7 节方案，用户本对话已倾向）？任务页 Tasks 来源二期是否也要？
3. **认证方案**：一级「一键 OAuth 重登」（推荐先做）还是先探平台 API key 体系/长时效凭证（二级）？
4. **工作项形态**：工作项看板按「workspace（项目空间）」还是「视图（view_queries）」组织？
5. **范围模块**：第一期只做「代码中心 + 工作项」，还是把「CI 状态/制品浏览」也纳入 L1？
6. **git 通道**：是否接受 Gerrit HTTP Password（用户自助生成）作为 git 长期通道？还是走 SSH 密钥（平台 auth/v1 管理）？

## 10. 结论

研发云与 Gitee 的集成路径完全同构：新增一个 provider 模块 + 注册表接线 + 独立 UI，无架构障碍。相比 Gitee 唯一的额外成本是**双后端双鉴权**（代码中心 + 工作项）与**内网可达性约束**；收益面更大（代码+评审+工作项+CI+制品全链路）。风险集中在认证令牌精确格式与接口稳定性，均有实测对策。建议先确认范围后从 L0 开工，L1 认证打通时用真实会话一次性抓包确认全部鉴权头。
