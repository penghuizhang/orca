# 移动端（Android/手机 App）探索分析与自建服务器中转改造方案

日期：2026-08-16
类型：调研分析 + 改造方案评估（未动代码）
分支：calendar-feature（本文档仅归档，与日历功能无关）

## 1. 结论摘要（TL;DR）

- Orca 移动端是 `mobile/` 目录下的 **React Native（Expo）配套 App**，功能是「远程遥控桌面 Orca」：查看 worktree/终端输出、发命令、审 PR、看任务、语音转写等。**它不是独立的数据客户端，所有数据都来自桌面端，手机本身不存业务数据。**
- 连接模型：手机直连桌面的 WebSocket 服务（端口 6768，同一 Wi-Fi/Tailscale），或经官方「Orca Relay」云中转（跨网络，需登录 Orca 云账号）。配对 = 扫桌面端生成的 QR 码（内容为 base64 编码的 JSON 配对要约）。
- **你「用自己的服务器中转」的需求，最可行的路径是不改任何代码**：在桌面端配一个自建反向隧道（frp 等），在设置里把配对地址改成你服务器的域名/端口，QR 码会自动通告该地址；手机经你的服务器中转后流量全部过你的平台，且由于鉴权是应用层的（设备令牌 + E2EE 加密），透明转发即可工作，无需改 App 或协议。
- 官方 Relay 协议（director + cell 两层）可以自研兼容实现，但是大工程（官方服务端不在本仓库，需按仓库内共享协议文档逆向重写），不推荐作为第一步。

## 3. 安卓端怎么使用（安装 / 配对 / 日常）

### 3.1 安装方式（三种）

1. **Expo Go（开发/快速体验）**：Google Play 装 Expo Go，`cd mobile && pnpm start`，手机扫码（需同一网络）。
2. **Dev client 构建（原生模块，开发）**：`pnpm exec expo run:android`（需要 Android Studio SDK），然后 `pnpm start --dev-client`。
3. **Release 构建（正式包）**：CI 有 `.github/workflows/mobile-android-release.yml`；`mobile/` 下无预生成 android/ 原生目录，由 Expo prebuild 在 CI 生成。包名 `com.stably.orca.mobile`（app.json），版本号 12。本地打正式 APK：`pnpm exec expo prebuild -p android && cd android && ./gradlew assembleRelease`（未实测，需 Android SDK/签名）。

### 3.2 配对流程（核心）

1. 桌面端打开 **Settings → Mobile**，选择连接方式：
   - **Orca Relay（自动）**：手机可在蜂窝网络/任意 Wi-Fi 连接；需登录 Orca 云账号（免费）；QR 码内含 relay 邀请。
   - **LAN（本地）**：手机与桌面同一 Wi-Fi 或经 Tailscale；无需账号。
   - 可下拉选择**网络接口地址**，也支持**自定义地址**（custom address，手动填 host:port 或 ws(s):// URL）。
2. 桌面生成 QR 码（`orca://pair?code=<base64url JSON>`），手机 App 首页点扫码（或粘贴配对码）→ 配对确认 → 完成。
3. 配对成功后手机保存该桌面为一个「host」条目，可改名/改地址/删除。

### 3.3 配对码内容（协议核心）

`orca://pair?code=` 后面是 base64url 编码的 JSON（`src/shared/mobile-relay-pairing-offer.ts` 的 `PairingOfferSchema` v2）：

```json
{
  "v": 2,
  "endpoint": "ws://192.168.1.10:6768",
  "deviceToken": "<随机设备令牌>",
  "publicKeyB64": "<桌面端 Curve25519 公钥>",
  "pairedDeviceId": "<设备ID>",
  "scope": "mobile",
  "relay": {   // 仅 Relay 模式存在
    "v": 1,
    "directorUrl": "https://relay.onorca.dev",
    "cellUrl": "https://<分配的中继单元>",
    "assignmentEpoch": 0,
    "relayHostId": "<16字符>",
    "inviteToken": "<43字符，10分钟有效>",
    "inviteExpiresAt": 1780000000000,
    "e2eeFraming": 2
  }
}
```

### 3.4 连接链路（两种通道）

**直连（LAN）**：手机 `new WebSocket('ws://<桌面IP>:6768')` → 首帧起跑 E2EE v2 握手（钉住桌面公钥，tweetnacl）→ 握手后每条消息带 `deviceToken` 校验 → JSON-RPC。终端流用二进制帧。

**Relay（跨网）**：手机先连 `wss://<directorUrl>/v1/connect/<relayHostId>`，发 `{type:'relay-auth', v:1, mode:'connect', credential: inviteToken}`，director 回 `relay-moved`（更新的 cellUrl）→ 手机再连 `wss://<cellUrl>/v1/connect/...` 建立 E2EE 通道 → 同一套 RPC。桌面端同样**主动出站**连到 cell 的 `/v1/host/control`（host-proof 挑战应答 + 控制连接），所以 NAT 内网桌面也能被手机找到——这是 Relay 的「打洞/中转」本质：**双方都主动连服务器**。

## 5. 自建服务器中转：三条可行路径

### 路径 A：透明反向隧道（推荐，零代码改动，半天可通）

**原理**：手机与桌面之间是「应用层鉴权 + 应用层加密」的普通 WebSocket，链路本身不需要任何 Orca 协议参与。在你自己服务器上跑一个 WebSocket 反向隧道（frp / 自写 node ws 转发），桌面端出站连到你的服务器，手机连到你的服务器，两端数据全部流经你的平台。

**实施步骤**：
1. 服务器（有公网 IP + 域名）：
   - 装 frps（或任意 TCP/WS 转发），监听如 `443/9443`，配 TLS 证书（Let's Encrypt）。
   - frp 需要支持 WebSocket 的纯 TCP 转发即可（WS 是 TCP 上的应用协议，透传无需解析）。
2. 桌面端：跑 frpc 客户端，把 `127.0.0.1:6768` 映射到服务器端口（出站连接，NAT 内网也能用）。
3. 桌面端 Settings → Mobile → 选 LAN（local-only）→ 地址选**自定义**，填 `wss://你的域名:端口`（或 `ws://`）→ 生成 QR。
4. 手机扫码（或手动改已配对 host 的地址）→ 正常配对/连接。

**为什么能透明工作**：
- 鉴权（deviceToken）在 JSON-RPC 消息体里，E2EE 握手是应用层协议，代理只看得到加密后的流量。
- `resolveAdvertisedPairingEndpoint` 支持任意 ws(s):// URL 覆盖；`isAllowedRelayOrigin` 对 relay 也没做官方域名白名单（虽然本路径不走 relay）。
- Android 端 `usesCleartextTraffic: true`（app.json），纯 `ws://` 明文链路也可用；但**建议 wss://**，否则设备令牌会被你的服务器（或任何中间人）看到并可重放——用 wss 后你的服务器也只能看到加密流量，无法解密内容（E2EE 密钥只有手机与桌面持有）。

**成本**：零代码改动；需要一台公网服务器 + 域名 + 证书；桌面端多跑一个 frpc 进程。风险极低，上游同步无冲突。

**注意事项**：桌面 WebSocket 监听默认只绑 loopback，但 frpc 就在本机，`127.0.0.1:6768` 可直连，无需担心 0.0.0.0 扩宽。

### 路径 B：自研兼容官方 Relay（大工程，暂不推荐）

- 官方 Relay = 「director（分配/邀请）+ cell（数据中继）」两级服务，**服务端代码不在本仓库**（生产地址 `https://relay.onorca.dev`，桌面端可用环境变量 `ORCA_RELAY_URL` 覆盖 director 地址）。
- 手机↔relay、桌面↔relay 的**客户端侧协议**在仓库内是公开的：`src/shared/mobile-relay-phone-protocol.ts`（relay-auth/relay-hello/relay-moved）、`src/main/runtime/relay/relay-control-protocol.ts`（host-challenge/host-hello-ack/conn-open 等）、`relay-control-url.ts`（`/v1/host/control`）、`relay-http-client.ts`（`/v1/assign`）。
- 若真要自建：需实现 director 的 `POST /v1/assign`、`WS /v1/connect/<relayHostId>` 与 cell 的双侧 WebSocket 服务、E2EE framing v2 透传、host-proof 挑战、租约/吊销语义，并处理桌面端 Orca 云账号登录换 token 的环节（可用 `ORCA_CLOUD_*` 系列环境变量指向自建账号服务，但 `isOrcaCloudDevAuthEnabled` 仅限非生产/未打包构建）。
- 工作量估计数周～数月，且协议随上游日更演进，维护成本高。**结论：只有当你要求「不依赖 frp 类第三方、完全自研协议栈」时才值得。**

### 路径 C：你的平台直接扮演「桌面端」角色（服务器成为数据源）

如果你的真实意图是「手机 App 的数据来源换成我自己的平台」（而不是流量中转），那么正确做法是：**你的服务器实现 Orca 的 WebSocket RPC 服务端**（监听 6768 同款协议：E2EE v2 握手 + deviceToken + JSON-RPC 白名单子集），手机 App 配对时地址直接填你的服务器。这样：
- 手机端**零改动**（协议完全兼容），你只需在服务器上实现服务端。
- 可只实现你要的方法子集（如 `terminal.*`、`worktree.*`、`git.*`、`status.get`），协议是 JSON-RPC + 共享类型（`src/shared/` 下均有 schema），可对照 `src/main/runtime/rpc/methods/` 逐个移植。
- 这本质上是「用服务器复刻 Orca 运行时」，属于大工程但边界清晰；注意 `MOBILE_RPC_METHOD_ALLOWLIST` 是移动端可调用的完整集合，实现子集后未实现的方法会返回错误，手机 UI 相应功能不可用。

### 路径对比

| 维度 | A 透明隧道（推荐） | B 兼容 Relay | C 服务器当数据源 |
|---|---|---|---|
| 代码改动 | **0** | 大（服务端全自研） | 大（服务端复刻运行时） |
| 数据是否经你平台 | ✅ 全部流量 | ✅ 全部流量 | ✅ 数据本来就在平台 |
| 服务器可见数据 | 仅加密流量（wss 时） | 仅加密流量 | 明文业务数据（可入库） |
| 可行性 | 半天 | 数周～数月 | 数周（子集） |
| 上游同步风险 | 无 | 高 | 中 |
| 适用 | 手机远程控制桌面（默认需求） | 完全去第三方依赖 | 手机 App 换成你的数据源 |

## 6. 约束清单（若后续实施必须逐条自查）

1. 【约束】路径 A 不改任何 Orca 代码（桌面/手机），只加 frp 类外部组件；改代码前必须先出方案评审。
2. 【约束】wss 必须用有效证书（Let's Encrypt），不引入自签证书（React Native 无法固定自签证书——官方用应用层 E2EE 代替 TLS 正是这个原因）。
3. 【约束】设备令牌与 E2EE 密钥随配对码走；配对码 10 分钟内有效（relay 邀请），QR 内容不要进日志/聊天记录。
4. 【约束】桌面端 6768 监听默认 loopback，配对时才扩 0.0.0.0；隧道客户端本机直连即可，无需改绑定策略。
5. 【约束】手机 App 手动改 host 地址的入口存在（app/h/[hostId]/edit.tsx），QR 之外的补救手段可用。
6. 【约束】若走路径 B/C，必须守住 `src/shared/` 的协议 schema 版本（PAIRING_OFFER_VERSION=2、e2eeFraming=2）与上游同步，避免旧 App 连不上。
7. 【约束】上游日更（约 66 commits/天），移动端协议文件属热文件；定制尽量「新增文件」，冲突面最小。

## 7. 建议下一步

1. 确认你的服务器是否有公网 IP/域名/证书（路径 A 的硬前提）。
2. 若确认走路径 A：先在测试机跑通 frp（服务器 frps + 桌面 frpc），再在 Settings → Mobile 用自定义地址生成 QR 验证手机连通。
3. 若想先看效果不动服务器：同一 Wi-Fi 直连（LAN 模式）已经可用，Relay 模式可先用官方账号体验跨网。
4. 路径 C 若才是你真正想要的（平台做数据源），建议先列「手机 App 上你真正需要哪几个页面/功能」，按方法子集评估工作量。
