## i18n 语言包：为什么不能「两边都留」

6 个文件 22 个冲突块，两种错法：

1. **闭合括号被吞**——对象的 `}` 在共享后缀里，两边直接拼会少一个 `}`，报
   `Expecting ',' delimiter` 且**行号指向文件末尾**。
2. **重复 JSON 键**——两侧常常新增**同名同值**的键（fork 把 `zcode_label` 放数组末尾，上游放在
   `muse_label` 旁边）。`json.load` 静默接受后者，UI 里渲染两次。

改用按键的三向语义合并（fork / upstream / merge-base）：并集优先，只在「两侧都改且值不同」时
打印出来交人工判定。格式零扰动——仓库语言包与
`json.dumps(obj, indent=2, ensure_ascii=False) + "\n"` 字节一致，整体重写后 diff 只含新增键。

## 门禁 `cross-version wire compatibility` 在 fork 里结构性地跑不通

```
Error: Cross-version harness found no stable desktop release tags matching vX.Y.Z (saw 0 tag(s) total).
Error: Cross-version harness could not resolve ref "v1.4.190" to a commit
```

该测试用**上游 stablyai/orca 的桌面发布 tag**（`v1.4.184`/`v1.4.190`/`v1.4.199`）与当前代码做 skew。
实测：**fork `penghuizhang/orca` 只有 2 个 tag（都是 `backup/pre-sync-*`）**，upstream 有 2181 个
⇒ GitHub checkout 永远解析不到 ⇒ **该门禁在 fork 里跑不通，且与源码无关**。

本地能过是因为本机 clone 里有上游 tag（本次会话开头强拉过）——**本地过 ≠ CI 能过**。

两条出路（CI 基础设施，需维护者拍板，本次未动）：
1. job 里加一步拉上游 tag：`git remote add upstream https://github.com/stablyai/orca.git && git fetch upstream 'refs/tags/*:refs/tags/*'`
   （保留真实 skew，代价是每次跑都拉大量 tag）
2. 设 `ORCA_CROSS_VERSION_BASELINE_REF` 指向 fork 内存在的 ref（便宜，但「旧客户端」不再是真正的旧发布）
