### 关键发现 1：首次 `git fetch upstream` 静默未更新引用

第一次 `git fetch upstream --tags` 返回 0 且无输出，但远程 `refs/heads/main` 实际已到 `b8f3b1ec00`，本地 `upstream/main` 仍停在 `01d7228b7e`。
改用显式 refspec 强拉后引用才更新：

```bash
git fetch upstream 'refs/heads/*:refs/remotes/upstream/*' --force
```

复用旧引用会导致「以为已是最新、实际两个月没同步」的假同步，**同步前必须核对 `git log -1 upstream/main` 的日期**。

### 关键发现 2：main 分支无法直接合并上游

`git merge-base main upstream/main` 返回空（无共同祖先）——浅克隆的 graft 边界（`.git/shallow` 10 条，2026-08-15 ~ 09-03）切断了 main 的历史。因此**文档中的 `upstream → main → custom` 三步流程在浅克隆下走不通**：main 那一步会因 “refusing to merge unrelated histories” 直接失败。

而 custom 与上游合并基为 `01d7228b7e`（正确的旧上游 tip），可直接合并。故本次**直接 `custom merge upstream/main`**，main 保持不动（它已是 custom 的祖先，且此前 PR #19 已把 custom 合进 main，不再是「纯净分支」）。

1. 提交工作区遗留知识产物（记忆 / 设计文档），保证合并前工作区干净；

## 七、第二轮：版本号「看起来是旧版」的根因与修复（用户反馈后追加）

### 7.1 现象与根因

用户反馈「构建版本为什么还是 197，最新应该 205 了」。根因**不是代码没同步**，而是版本号基数计算机制 + 本地 tag 过期：

```js
// config/scripts/build-mac-local.mjs
version = createLocalBuildVersion(resolveVersionBase(packageJson.version), Date.now(), commit)
// resolveVersionBase = max(package.json 版本, 本地最高纯 vX.Y.Z tag)
```

1. **上游 `main` 的 package.json 长期落后于发版号**：实测 `upstream/main` = `1.4.197`，而远端发布 tag 已到 **`v1.4.206`**。`release: v1.4.206` 提交**不在 main 历史里**（发版走 release 分支 + tag，见 `.github/workflows/release-cut.yml` 的 `commit_message="release: v$VERSION"`）。⇒ 用 main 的 package.json 判断新鲜度是错的。
2. **本地 tag 列表过期**：本地 tag 最高只到 `v1.4.197`（同样是浅克隆下 fetch 静默过期所致）⇒ `resolveVersionBase` 取到 `1.4.197`，于是**代码已是最新、版本号却看着像旧的**。

### 7.2 修复动作

| 动作 | 结果 |
|------|------|
| 核对远端 tag 真相（`git ls-remote --tags upstream`） | 远端最高纯版本 tag = **v1.4.206** |
| 拉取该 tag（`git fetch upstream refs/tags/v1.4.206:refs/tags/v1.4.206`） | 本地 tag 到位（v1.4.198~205 仍缺，**不影响**版本基数，只补最高即可） |
| 验证基数（直接调用 `resolveVersionBase`） | ✅ 输出 `1.4.206` |
| 顺带追平上游最新 6 个提交（`e2afb5eef9`） | 合并提交 `b4d72ff19e`；1 个冲突：`usage-provider-contract.ts` 上游加 `'devin'`、二开有 `'zcode'/'pi'` ⇒ 取并集 |
| 重跑 `pnpm install`（6 提交含 +81 行锁文件） → `pnpm tc`（exit 0）→ `verify-features`（VERIFY_EXIT=0） | ✅ 全绿 |
| 重建 + 安装 | ✅ **`1.4.206-local.1789785189109.117aa480069c`**（签名校验 exit 0） |

### 7.3 结论

- 修复后版本号 `1.4.206-local.<时间戳>.<commit>`，与上游发版号对齐；`package.json` **保持上游的 1.4.197 不动**（避免每次同步在版本行上产生冲突，版本基数由 tag 机制承担）。
- **打包前应核对**：`resolveVersionBase` 的输出是否 ≥ 远端最新发布 tag。教训与命令见 `pitfalls/orca-build-version-base`。
- **仍需用户手动重启 orca-s** 才会运行 `1.4.206`（原因同 §6.4 第 2 条：本会话跑在 orca-s 终端内，且 macOS 不替换运行中进程）。
