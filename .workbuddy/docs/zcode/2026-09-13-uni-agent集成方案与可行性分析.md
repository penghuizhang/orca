# uni-agent 集成 Orca 方案与可行性分析

- 日期：2026-09-13
- 类型：可行性调研 + 集成设计（**待评审；本文档不含任何代码实施**）
- 前置调研：`/Users/zhangpenghui/code/aistudy/2026/diy_voice/docs/调研分析/2026-09-13-uni-agent在CLI与ORCA中的集成可行性调研.md`（已确认「HBuilderX CLI 可编程调用 uni-agent」这条路能跑通）
- 类比对象：`.workbuddy/docs/zcode/2026-08-16-新增zcode智能体类型设计方案.md`（用户预期：uni-agent 像 zcode 一样是一个可用工具）

## 一、结论（先说结果）

**能集成，但做不到「像 zcode 那样直接注册一个 TuiAgent 就完事」。** 原因是双方模型错位：

- uni-agent 官方 CLI 是**一次性（one-shot）命令**，而且它本质是 **HBuilderX 进程的本地 socket 客户端**——不是独立 agent runtime；模型、密钥、会话都在 HBuilderX 那一侧。
- Orca 的智能体模型 **100% 要求「长驻交互进程」**，没有任何 one-shot agent 执行通道。

所以「像 zcode 一样在 Orca 里对话」**必须在中间加一层 PTY 桥接薄壳（wrapper）**，把一次性 CLI 包装成长驻交互会话。这层壳是我们自己写、自己维护的。

如果接受「不写壳、退化成一次性问答」，也可以零壳注册，但体验与 zcode 差距明显（见 §6.5 R2a）。

| 维度 | zcode | uni-agent |

| 模型/密钥 | 自己的配置 | HBuilderX 全局设置 |

## 四、三条候选路线

| 路线 | 形态 | orca 改动量 | 体验 | 适用 |
|---|---|---|---|---|
| **R1 终端派单（零代码）** | 在 Orca 终端里直接跑 `cli uni-agent …`；或 `orca terminal create --command "…"` | 0 | 原始 CLI，无 agent 卡片/状态 | 今天就能用；用于验证假设 |
| **R2 原生 agent（wrapper + 注册 TuiAgent）** | 写一个 `uni-agent` 交互壳，注册进注册表 | 约 15 文件 + 1 个壳 | **最接近 zcode** | 用户目标：像 zcode 一样用 |

## 五、推荐路线：分两阶段，Phase 1 先验证再动代码

**Phase 1（本次评审通过后第一步，零 orca 代码）**：用 R1 打通并验证 §7 的 5 个未验证假设。只有假设成立，Phase 2 才有意义。
**Phase 2（目标）**：落 R2——写 wrapper + 注册 TuiAgent。
**R3（可选，二期）**：有跨 agent 协作需求再做。

不建议直接上 Phase 2：R2 的成本主要在 wrapper，而 wrapper 的形态完全取决于 Phase 1 的验证结论（尤其「无 GUI 能否跑」与「写操作是否卡确认」）。

## 六、R2 详细设计（目标方案）

### 6.1 wrapper 行为规格

壳名建议 `uni-agent`（放 PATH，如 `~/.local/bin/uni-agent`），行为：

```
进入壳 → 打印 banner + 提示符 "uni-agent>"
  读取一行输入
  首次：cli uni-agent --project <cwd> --prompt <text> --output-format stream --show-progress true
  后续：同上 + --continue true        # 同一 session 续接
  将子进程 stdout/stderr 原样透传到 PTY
  子进程退出 → 回到提示符，等待下一轮
Ctrl+C → 中断当前轮（kill 子进程），不退出壳
Ctrl+D / exit → 退出壳
```

要点：
- `--project` 取 Orca 传入的工作目录（worktree/folder cwd）。**HBuilderX 只认项目名或项目绝对路径**，需先确认该目录在 HBuilderX 里是已打开项目；否则要给出可读报错而非静默失败。
- 默认**不加** `--yolo`（见 §7 风险）。是否自动授权交给用户环境变量开关，例如 `UNI_AGENT_YOLO=1`。
- stdout 透传保证 Orca 终端能看到流式输出；`--show-progress true` 打印思考/工具过程。

### 6.2 注册配置（`src/shared/tui-agent-config.ts`）

```ts
'uni-agent': {
  detectCmd: 'uni-agent',        // PATH 上的 wrapper；可用绝对路径兜底
  launchCmd: 'uni-agent',
  expectedProcess: 'uni-agent',
  // Why: 上游 CLI 是一次性（--prompt 执行完即退出），无 TUI；Orca 只能启动长驻壳后粘贴。
  promptInjectionMode: 'stdin-after-start'
}
```

> ⚠️ 待实测：壳的提示符就绪信号能否支撑 bracketed paste（对齐 zcode 的 `draftPasteReadySignal` 待验证项）。壳是我们自己写的，**可以主动输出一个就绪标记**来消除这个不确定性——这是自研壳的优势。

### 6.4 与 zcode 集成的差异（风险集中在哪）

| 差异点 | 影响 |
|---|---|
| 上游无 TUI | 必须自研 wrapper；zcode 零壳 |
| 上游是 app 包内 socket 客户端 | 依赖 HBuilderX 运行；换机/CI 需先装 HBuilderX |
| 远端宿主不可检测 | SSH/WSL/远端 workspace 下该 agent 不会出现，属预期 |
| 会话在 HBuilderX 侧、全局共享 | 多项目/并发共享同一套 key 与权限设置 |
| 无 `--resume` | 不做会话恢复集成 |

### 6.5 R2a（零壳降级方案，备选）

若不想写壳：直接把上游一次性命令注册为 `promptInjectionMode: 'argv'`。结果是「选中 uni-agent → 跑一轮 → 进程退出」，无后续轮次、无 `--continue` 串联。**成本最低但体验与 zcode 明显不同**，仅在「只想要一次性问答」时采用。

## 七、风险与坑（实施前必读）

1. **依赖 HBuilderX 运行**：E3/E4 强烈提示 `cli` 是本地 socket 客户端。前置调研把「GUI 完全没启动时能否跑通」标为未验证——**这是 Phase 1 第一件要测的事**。
2. **`--yolo` 很危险**：官方警告会无监督改文件。默认不开；若要自动化必须确保工作区干净（`enlighten_appx/` 有并行会话在改）。
3. **写操作是否卡人工确认**：默认模式改文件/跑命令会等确认；`permissionAutoAllow=true` 下是否真不卡，**未验证**。用「创建一个临时文件」的 prompt 验证。
4. **并发安全未验证**：同一 HBuilderX 进程被多个壳同时调用是否安全未知。
5. **多行 prompt**：壳按行读输入，Orca 粘贴多行会被拆成多轮。一期可先只支持单行/转义 `\n`。
6. **`--project` 语义强约束**：目录必须在 HBuilderX 中作为项目存在，否则失败。
7. **模型配置全局**：CLI 走 HBuilderX 全局设置，无法按 Orca 工作区隔离。
8. **上游日更冲突**：注册表散在约 15 个文件、且上游天天改，需按 `orca-dev-workflow` 走 feature 分支 + PR。

## 八、验收标准

Phase 1（R1，零代码）：
1. 无 GUI / 有 GUI 两种情况分别验证 `cli uni-agent` 可用性，结论落文档
2. 验证写操作是否卡确认（`permissionAutoAllow=true`）
3. 验证两路并发调用是否互不干扰
4. 采集 `--output-format stream` 的实际分帧样本，确认适合透传

Phase 2（R2）：
1. `pnpm tc` 与相关单测全绿
2. 新工作区 agent 选择器出现 uni-agent，图标/名称正确；tab 输入 `uni-agent` 可模糊命中
3. 未装 HBuilderX 的机器检测为「未安装」
4. Orca 内选中后进入壳，能多轮对话（第二轮 `--continue` 生效，能忆起上一轮）
5. 远端/SSH 工作区不出现该 agent（预期行为）
6. telemetry 事件 `agent_kind` 正确

## 九、一期不含

- MCP 薄壳（R3）
- 会话恢复 / native chat 会话卡片（上游无 `--resume`）
- 用量统计面板（对齐 zcode 的 usage provider 需另做，属独立功能）
- commit message 生成、OSC 标题识别等周边
- 任何形式的 `--yolo` 默认开启

## 十、约束清单（实施自查）

- 【约束】必须先做 Phase 1 验证，5 个假设有结论后才动 orca 代码
- 【约束】所有 `satisfies Record<TuiAgent, …>` 完备 map 必须补条目，交给 `pnpm tc` 兜底
- 【约束】i18n 六语言（en/zh/es/fr/ja/ko）都要补，不得只改 en；改完大 JSON 必须 `json.load` 校验（历史坑：en.json 被破坏致打包失败）
- 【约束】默认不加 `--yolo`；自动化权限不由本次开通
- 【约束】不新增 `max-lines` disable（AGENTS.md 规则）；注释只写 WHY
- 【约束】不改 HBuilderX 打包产物、不动 `/usr/local/bin/orca` 等外部工具链
- 【约束】功能改动走 feature 分支 + PR → custom，不直推
- 【约束】跨平台：壳需在 macOS/Linux/Windows 均可运行，路径用平台 API；检测依赖 PATH

## 十一、开放问题（需拍板）

1. **是否接受「自研 wrapper 壳」？** 这是 R2 的前置成本。不接受则只能 R1（终端派单）或 R2a（一次性降级）。
2. **壳放哪、谁维护？** 建议放工程内 `.agents/scripts/` 或独立小包，避免进 orca 主构建。
3. **Phase 1 是否需要现在就跑？** 涉及启停 HBuilderX（当前 GUI 正在运行），需确认可打扰窗口。
4. **R3（MCP 外包）是否列入二期？** 取决于是否有「让 claude/zcode 调 uni-agent」的真实需求。
