# 状态栏「状态栏出现错误」根因分析与修复建议

- 日期：2026-09-12
- 类型：线上缺陷根因分析 + 影响说明 + 修复实施记录（**已实施并打包验收通过**）
- 涉及构建：`1.4.197-local.1789117402985.5c7059fdce89`（2026-09-11 打包，见 `daily/2026-09-11.md`）
- 上游同名修复：stablyai/orca `5412276776fb` *Fix status bar runtime target render loop (#18685)*（2026-09-04）

## 一、结论（一句话）

新版打包（1.4.197）状态栏整条崩掉，是**上游 #17048 引入的 zustand v5 selector 引用不稳定**导致 React 无限重渲染（minified React error #185），首个受害者是状态栏里常驻挂载的 `PortsStatusSegment`；上游已在 `5412276776fb` 修掉，但**我们合并的上游快照不含这个修复**（已用 `git merge-base --is-ancestor` 验证为 ABSENT）。

## 二、现象

- 底部状态栏区域被错误边界兜底替换：红色警告图标 + 「状态栏出现错误。」+「重试状态栏以重新挂载其控件。」+「重试」按钮。
- 兜底 UI 由 `src/renderer/src/app-shell/AppRootSurfaces.tsx:175-185` 的 `OverlayBoundary`（`boundaryId="overlay.status-bar"`）渲染，说明**状态栏子树在渲染期抛异常被边界捕获**，不是启动失败、不是 chunk 加载失败。

## 三、证据链（来自本机打包版崩溃记录）

来源：`~/Library/Application Support/orca-s/crash-reports.json`（`orca-s` = com.penghuizhang.orca-s，时间戳 09:22 与截图 09:23 吻合）

| 字段 | 值 |
|---|---|
| `appVersion` | `1.4.197-local.1789117402985.5c7059fdce89`（与 2026-09-11 打包产物一致） |
| `details.boundary_id` | `overlay.status-bar` |
| `details.error_message` | `Minified React error #185; ... Maximum update depth exceeded` |
| `details.attribution` | `unreliable`（#185 的权威归属不可信，见 `src/shared/react-update-depth-attribution.ts`） |
| `details.component_stack` | `at Y (PortsStatusSegment-BrJIPbyx.js) → Suspense → div → div → Jn (StatusBar) → RecoverableRenderErrorBoundary` |

`attribution: unreliable` 的含义：React 的 nested-update 计数器是**模块级全局**的，超过阈值 50（`REACT_NESTED_UPDATE_LIMIT`）后，抛到「下一个调用 setState 的组件」身上。所以 `component_stack` 里的 `PortsStatusSegment` 可能只是**恰好被选中的当事组件**，不能只凭它断定死循环发源地——真正的定位靠下面的代码比对。

## 四、根因

### 4.1 引入点：上游 commit `7574ee8403`（PR #17048）

该 commit 把「四个 ports 界面各写一遍的 owner-settings 展开」抽成公共 hook，新增文件 `src/renderer/src/runtime/use-worktree-runtime-target.ts`：

```ts
export function useWorktreeRuntimeTarget(worktreeId: string | null | undefined): RuntimeClientTarget | null {
  return useAppStore((state) =>
    runtimeTargetForExecutionHostId(getExecutionHostIdForWorktree(state, worktreeId))
  )
}
```

`runtimeTargetForExecutionHostId()` 每次都**返回新的字面量对象**（`{ kind: 'local' }` 或 `{ kind: 'environment', environmentId }`，见 `runtime-client-target.ts:14-25`）。

### 4.2 触发机制：zustand v5 的 snapshot 必须引用稳定

实装版本 `zustand@5.0.14` 的 `useStore` 直接用裸 `React.useSyncExternalStore`，**没有** v4 的 `useSyncExternalStoreWithSelector` 记忆化层：

```js
const slice = React.useSyncExternalStore(
  api.subscribe,
  React.useCallback(() => selector(api.getState()), [api, selector]),
  ...
)
```

selector 每次返回新对象 ⇒ `getSnapshot()` 结果永远与已渲染值不等 ⇒ React 在 commit 阶段持续判定 "snapshot 变了" 并再次强制渲染 ⇒ nested update 计数越过 50 ⇒ **React error #185 Maximum update depth exceeded**。这是 zustand v5 迁移指南明确点名的坑（v4 会按 `Object.is` 记忆化 selector 结果，所以同样写法在 v4 不炸）。

### 4.3 对照：旧代码是稳定的，所以是「新版本才有」

同一个组件在 `7574ee8403` 之前的写法是**先选稳定引用、再 useMemo 派生**：

```ts
const settings = useAppStore((s) => s.settings)          // 稳定引用
const runtimeTarget = useMemo(() => getActiveRuntimeTarget(settings), [settings])  // 派生被记忆化
```

改造后这层记忆化被 hook 内部的「新对象」取代，稳定性丢失。**这正是 1.4.178-rc.2（上一次能用的包）到 1.4.197（这次崩的包）之间状态栏代码的唯一变化**——`git diff main...custom -- src/renderer/src/components/status-bar` 只列出 ports 这 4 个文件。

### 4.4 为什么只有状态栏炸、其他 ports 界面表面正常

新 hook 共 4 处消费者，全都会触发同一个死循环，区别只在**是否常驻挂载**：

| 消费者 | 挂载条件 | 新版本表现 |
|---|---|---|
| `components/status-bar/PortsStatusSegment.tsx:40` | 状态栏常驻（`showPorts`） | **启动即炸**（用户看到的现象） |
| `components/status-bar/ports-status-popover-rows.tsx:86`（`PortRow`） | 打开 ports 弹层 | 打开弹层时炸 |
| `components/sidebar/WorktreeCardPorts.tsx:109`（`WorktreePortRow`） | 侧栏工作区卡片有端口时 | 展开该卡片时炸 |
| `components/right-sidebar/local-workspace-ports-panel.tsx:48` | 右侧栏 Ports 面板打开 | 打开面板时炸 |

即：**这不是「状态栏一个控件坏了」，而是四处同源缺陷，状态栏只是最先且必然命中的那个。**

## 五、修复建议

上游已修，改动极小（+3/-3）且带回归测试。建议**直接取上游修复**，不自行改写（避免与上游分叉）。

### 方案 A（推荐）：cherry-pick 上游修复

```bash
git fetch upstream          # 或 origin（fork 上有同步）
git cherry-pick 5412276776fb   # 可能需先补 fetch 到该 commit
```

含 2 个文件：
1. `src/renderer/src/runtime/use-worktree-runtime-target.ts`（+3/-3）——先选字符串、再用 `useMemo` 派生：

```ts
const executionHostId = useAppStore((state) => getExecutionHostIdForWorktree(state, worktreeId))
return useMemo(() => runtimeTargetForExecutionHostId(executionHostId), [executionHostId])
```

2. `src/renderer/src/components/status-bar/PortsStatusSegment.render-stability.test.tsx`（新增 +89）——用真实 `useAppStore` + 真实 `RecoverableRenderErrorBoundary` 渲染 `PortsStatusSegment`，断言「不出现兜底文案」且「不出现 Maximum update depth exceeded」，是这条缺陷的防回归网。

> 要点：`getExecutionHostIdForWorktree()` 返回 `ExecutionHostId`（字符串联合类型，`src/shared/execution-host.ts:9`），是**原始值**，可作为 selector 输出与 `useMemo` 依赖；对象派生必须留在 selector 之外。

### 方案 B（不推荐）：本地手改一行

只把 hook 改成 `useMemo` 也能修掉现象，但会丢掉上游的回归测试，且下次同步上游时产生同文件冲突。仅在无法拉取上游 commit 时使用。

## 七、约束清单（实施时逐条自查）

- 【约束】只允许取上游 `5412276776fb` 的两个文件，不得顺手重构 `PortsStatusSegment.tsx` 的其他部分
- 【约束】不得往 main/master/orca 提 PR（fork 二开约定，见 `reference/orca-fork-2dev.md`），改动只落 custom 分支
- 【约束】selector 输出保持原始值/稳定引用；任何返回新对象的派生必须放在 selector 之外（`useMemo`/`useShallow`）
- 【约束】不改 zustand 版本，不改 `useWorktreeRuntimeTarget` 的函数签名与返回类型（4 处调用方零改动）
- 【约束】新增测试必须走真实 store，禁止 mock 掉 `useAppStore`（mock 掉就失去对 selector 稳定性的覆盖）
- 【约束】验收必须在**打包安装版**上做，dev 下的 React 只会打印 `getSnapshot should be cached` 警告、不会崩，容易误判为「没问题」

## 八、影响面与风险

- **影响面**：仅 ports 相关 4 处消费者；不涉及主进程、IPC、schema、远程协议，热修风险低。
- **风险**：`useMemo` 依赖 `executionHostId` 字符串，语义与原实现一致（同一个 worktree → 同一个 host id），无行为变更；`runtimeTargetForExecutionHostId` 仍可能返回 `null`（直连 SSH owner），调用方已有 `!runtimeTarget` 分支。
- **同类隐患提示**：这次是「selector 返回新对象」，值得作为一类模式排查——仓库内已有 92 处使用 `useShallow` 的正确示范，可在后续巡检中扫一遍「selector 内直接构造对象/数组且未 `useShallow`」的写法。
